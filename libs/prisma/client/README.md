# @kookio/prisma-client

Prisma schema and **server-only data-access layer** for the monorepo. This package owns:

- `schema.prisma` and migrations (CockroachDB).
- Generated **Prisma Client** and **co-located Zod schemas** (consumed via `@kookio/prisma-client/prisma-zod-generator`).
- Repository abstractions (e.g., `PrismaIngredientRepository`) with Cockroach-friendly retry semantics (`withTxRetry`).
- Operational scripts (e.g., `src/scripts/seed.ts`) and SQL helpers (`SQLs/bootstrap_cockroach.sql`).

> **Usage guideline:** the root of `@kookio/prisma-client` is **server-only** (Prisma runtime + repositories).  
> For **Zod validation** at UI/tRPC boundaries, import **exclusively** from the isomorphic `@kookio/prisma-client/prisma-zod-generator`.  
> For DTO helpers, use the **dedicated** isomorphic subpath `@kookio/prisma-client/dtos`.  
> This keeps browser bundles free of Prisma runtime and maintains a clean dependency graph.

## Zod schemas (co-located & isomorphic)

- The [prisma-zod-generator] runs during `npx prisma generate` and writes to  
  `./src/prisma-zod-generator/schemas`.

- `./src/prisma-zod-generator/index.ts` re-exports only the **public** API (no Prisma runtime imports), so it’s safe for frontend consumption.

**Example `./src/prisma-zod-generator/index.ts`:**

```ts
export * from './schemas/index';
/**
 * !! -- Keep this order of exports in order to apply overrides correctly -- !!
 */
export { IngredientFindManyResultSchema } from './overrides/ingredients';
```

**Generator snippet in `schema.prisma`:**

```prisma
generator zod {
  provider = "prisma-zod-generator"
  output   = "./src/prisma-zod-generator"
}
```

_Optional:_ the `.prisma-zod-generator-manifest.json` can be used in CI to check freshness or to drive Nx cache inputs.

## Database architecture

### Environments & databases

Three isolated CockroachDB databases on a single Basic-plan cluster
(`eu-central-1`):

| Database      | Consumers                                  | Writes from                |
| ------------- | ------------------------------------------ | -------------------------- |
| `kookio_dev`  | Local dev + Vercel Preview on `dev` branch | Developers, seed           |
| `kookio_test` | Vercel Preview on `test` branch + E2E runs | E2E fixtures, seed         |
| `kookio_prod` | Vercel Production on `main` branch         | End users, migrations only |

### Roles

Two dedicated roles per database (principle of least privilege):

- **`kookio_app`** — runtime role used by the Analog app and tRPC server.
  Privileges: `SELECT`, `INSERT`, `UPDATE`, `DELETE` on all tables.
  Cannot run DDL.
- **`kookio_migrate`** — migration role used exclusively by the
  `prisma-migrate` composite Action in CI/CD. Privileges: full DDL +
  DML. Never used at runtime.

This separation ensures that a compromised app role cannot `DROP TABLE`
or otherwise alter the schema.

### Credentials

| Where              | Used by                         | Secret name(s)                                       |
| ------------------ | ------------------------------- | ---------------------------------------------------- |
| Vercel env vars    | Analog app at runtime           | `DATABASE_URL`, `DIRECT_DATABASE_URL`                |
| GitHub env secrets | CI/CD (`prisma migrate deploy`) | `KOOKIO_APP_CONNECTION`, `KOOKIO_MIGRATE_CONNECTION` |

- Connection strings always include `sslmode=verify-full`.
- `DIRECT_DATABASE_URL` is used by Prisma Migrate (bypasses the pooler);
  `DATABASE_URL` is used by the app (uses the CockroachDB built-in pooler).
- Credentials are **never** committed to the repo. Local development pulls
  them via `npx vercel env pull`.

### Migration flow

1. Developer edits `schema.prisma` on a feature branch
2. Run `npm run migrate-dev-create-only:prisma-client` — review the generated SQL
3. **Cockroach gotcha**: if Prisma generated a spurious
   `DROP TYPE "public"."crdb_internal_region";` line (happens when adding new
   enums), delete it manually before proceeding — otherwise the migration will
   fail with error `P3018` / `2BP01`
4. Run `npm run migrate-dev:prisma-client` to apply + regenerate client
5. Commit the migration files, open PR against `dev`
6. Merge `dev` → `test` → `main`; CI applies the migration to each database via
   the `prisma-migrate` composite Action
7. Production migration requires manual approval (GitHub Environment
   protection on the `production` environment)

### Bootstrap

The script that creates the three databases + roles from scratch lives in
`SQLs/bootstrap_cockroach.sql` (plus the TypeScript wrapper in
`scripts/bootstrap-cockroach.ts`).

## Data model overview

**Interactive ER diagram**: [dbdocs.io/dinea.eduard/kookio-db](https://dbdocs.io/dinea.eduard/kookio-db?schema=public&view=relationships) — password protected (ask maintainer)
**Offline PDF**: [`../../../Kookio_DB_Diagram.pdf`](../../../Kookio_DB_Diagram.pdf)
**DBML source**: [`../../../kookio.dbml`](../../../kookio.dbml)

The schema contains **21 models** grouped into five functional domains:

### 1. Authentication & Identity

| Model                | Purpose                                                       |
| -------------------- | ------------------------------------------------------------- |
| `User`               | Core account — email, name, roles, soft-delete, disabled flag |
| `WebAuthnCredential` | Passkey credentials for passwordless auth                     |
| `UserProfile`        | Per-user preferences: household size, onboarding status       |

### 2. User preferences

Join tables connect users to the reference catalogs:

| Model                    | Links                                                |
| ------------------------ | ---------------------------------------------------- |
| `DietaryRestriction`     | Reference table (vegan, gluten-free, etc.)           |
| `UserDietaryRestriction` | Join — composite PK `(userId, dietaryRestrictionId)` |
| `Utensil`                | Reference table (oven, blender, etc.)                |
| `UserUtensil`            | Join — composite PK `(userId, utensilId)`            |

### 3. Recipe catalog (read-heavy, seeded)

Sourced from TheMealDB, seeded across all environments.

| Model               | Purpose                                                                                |
| ------------------- | -------------------------------------------------------------------------------------- |
| `Recipe`            | Central entity — title, instructions, servings, times, author, status (PUBLIC/PRIVATE) |
| `MealCategory`      | TheMealDB classification (Beef, Dessert, etc.)                                         |
| `MealArea`          | Cuisine (Italian, Japanese, etc.) with flag emoji                                      |
| `IngredientCatalog` | Master ingredient list (~871 rows) with category enum                                  |
| `RecipeIngredient`  | Join — `(recipe, ingredient)` with `quantity` + `unit` + optional notes                |
| `RecipeTag`         | Free-form tags for search/filter                                                       |

### 4. User cooking (write-heavy, per-user)

| Model                   | Purpose                                                           |
| ----------------------- | ----------------------------------------------------------------- |
| `PantryItem`            | What's in the user's pantry — ingredient + quantity + `expiresAt` |
| `RecipeCollection`      | User's custom recipe lists (favorites, themed collections)        |
| `RecipeCollectionEntry` | Join — composite PK `(collectionId, recipeId)`                    |
| `CookingSession`        | Audit trail — user cooked recipe at timestamp                     |

### 5. Meal planning

| Model          | Purpose                                                                               |
| -------------- | ------------------------------------------------------------------------------------- |
| `MealPlan`     | A named date-range plan owned by a user                                               |
| `MealPlanSlot` | Individual slot — date + meal type (BREAKFAST/LUNCH/DINNER/SNACK) + recipe + servings |

### Enums

| Enum                 | Values                                                                                                                                                                                                      |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Role`               | `USER`, `ADMIN`                                                                                                                                                                                             |
| `RecipeStatus`       | `PUBLIC`, `PRIVATE`                                                                                                                                                                                         |
| `MealSlotType`       | `BREAKFAST`, `LUNCH`, `DINNER`, `SNACK`                                                                                                                                                                     |
| `IngredientCategory` | `MEAT`, `FISH`, `DAIRY`, `PRODUCE`, `GRAINS`, `LEGUMES`, `SPICES`, `CONDIMENTS`, `HERBS`, `NUTS`, `BEVERAGES`, `OTHER`                                                                                      |
| `MeasureUnit`        | 18 values — metric (`G`, `KG`, `ML`, `L`), imperial (`OZ`, `LB`), cooking (`TSP`, `TBSP`, `CUP`, `PINCH`, `PIECE`, `SLICE`, `CLOVE`, `BUNCH`), and qualitative (`TO_TASTE`, `TO_SERVE`, `GARNISH`, `OTHER`) |

## Schema change patterns

All schema changes go through Prisma Migrate. Follow these patterns to avoid
breaking production.

### Adding a nullable column — safe, single migration

Add the field as nullable:

```prisma
model Recipe {
  // ...existing fields
  difficulty String? // new, nullable
}
```

Deploy order: migration + code can deploy together.

### Adding a NOT NULL column — expand-contract over 2 releases

**Release 1** — add as nullable with a default:

```prisma
difficulty String @default("MEDIUM")
```

**Release 2** — after backfill is complete and all writers populate the field,
remove the default if desired:

```prisma
difficulty String // now required, no default
```

### Renaming a column — expand-contract over 3 releases

1. Add the new column alongside the old one
2. Dual-write: update app code to write to both columns; backfill historical data
3. Update reads to prefer new column
4. Drop the old column

### Dropping a column — expand-contract over 2 releases

1. Remove all reads + writes from app code; deploy
2. Drop the column in a follow-up migration

### Adding an enum — gotcha

When adding a new `enum` to `schema.prisma`, Prisma may generate a spurious
`DROP TYPE "public"."crdb_internal_region";` line in the migration SQL. Always
use `migrate-dev-create-only` first, review the SQL, delete that line if present,
then run `migrate-deploy`. See the full recovery procedure in
[`.ai/12_prisma-zod.md`](../../../.ai/12_prisma-zod.md) under
"CockroachDB: spurious `DROP TYPE` on new enums".

### Adding a composite unique constraint

CockroachDB creates a new index; this is non-blocking but may take time on
large tables. Prefer off-peak deploys for migrations on tables larger than 1M
rows.

### Never do this

- `DROP TABLE` without a multi-release deprecation
- `ALTER COLUMN` type changes (requires table rewrite on Cockroach — use
  expand-contract with a new column instead)
- Renaming an enum value (not supported — create a new value, migrate data, then
  remove the old one across two releases)

## Nx targets & scripts

| Command                           | Description                                                                                 |
| --------------------------------- | ------------------------------------------------------------------------------------------- |
| `nx generate prisma-client`       | Runs `npx prisma generate` (keeps Prisma Client and Zod schemas up to date).                |
| `nx migrate-dev prisma-client`    | Runs `prisma migrate dev` from the workspace root.                                          |
| `nx migrate-deploy prisma-client` | Runs `prisma migrate deploy` (CI/production).                                               |
| `nx seed prisma-client`           | Executes `src/scripts/seed.ts`                                                              |
| `nx studio prisma-client`         | Opens Prisma Studio.                                                                        |
| `nx build prisma-client`          | Compiles TS via `@nx/js:tsc`; **depends on** `generate` to ensure schemas exist beforehand. |
| `nx test prisma-client`           | Vitest harness (lightweight).                                                               |

## Usage

### Server (repositories + boundary validation in tRPC)

```ts
// server-only data-access
import { prisma, PrismaIngredientRepository } from '@kookio/prisma-client';

// zod validation (isomorphic, safe for FE as well)
import { IngredientCreateOneSchema, IngredientFindManyResultSchema } from '@kookio/prisma-client/prisma-zod-generator';

// optional DTO helpers (shape transformations, result wrappers)
import { IngredientCreateOneResultDto } from '@kookio/prisma-client/dtos';

const repo = new PrismaIngredientRepository();
await repo.create({
  data: { userId: 'seed', name: 'Flour', quantity: 1, unit: 'kg', optional: false },
});

// example tRPC usage
ingredientRouter.input(IngredientCreateOneSchema).output(IngredientFindManyResultSchema);
```

### Frontend (Angular/Analog)

```ts
import { IngredientFindManyResultSchema } from '@kookio/prisma-client/prisma-zod-generator';
// Optionally: import DTOs if you expose UI-oriented aggregations
import { IngredientFindManyResultDto } from '@kookio/prisma-client/dtos';

// Do NOT import from @kookio/prisma-client in FE.
```
