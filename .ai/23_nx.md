# NX Guidelines

> **Status: Active** — NX v21+ monorepo with `@nx/angular` and `@nx/js` generators; `@kookio/*` import paths and `@nx/enforce-module-boundaries` are in use. The library organization is **scope-first** (`libs/{core,feature,prisma,server,shared}`), not the classic NX `ui / data-access / util / types` taxonomy. The "Library Organization" section below is the authoritative "where does a new lib go?" guide, and the rules under "Dependency Boundaries" are quoted verbatim from `eslint.config.mjs`.

## Version

NX v21+

## Library Organization

Libraries are grouped **by scope, then by domain** — there is **no**
`data-access`, `util`, or `types` lib type. The full tree is in
`10_architecture.md`; the "where does a new lib go?" summary:

| Group     | Holds                                                               | Example libs                     |
| --------- | ------------------------------------------------------------------- | -------------------------------- |
| `core`    | Cross-cutting infra, framework-light, no domain knowledge           | `core/logging`                   |
| `feature` | A domain's Signal Stores + UI + routing surface together            | `feature/pantry`, `feature/auth` |
| `prisma`  | Persistence — extended client, generated Zod schemas, derived types | `prisma/client`                  |
| `server`  | Server-only code; never imported from the browser                   | `server/trpc`, `server/auth`     |
| `shared`  | Stateless reusable pieces; no feature DI, no router dependency      | `shared/ui`, `shared/utility`    |

- **No `data-access` lib** — a domain's stores and services live inside its
  `feature/<domain>` lib, next to the components that consume them.
- **No `types` lib** — types live with the code that owns them
  (`libs/prisma/client/src/lib/types/`, `libs/feature/shell/src/lib/models/`).
- **`util` is named `utility`** here (`shared/utility`).

### Scope tags drive the enforced boundary

Each `project.json` carries a `scope:*` tag, and the directory group does
**not** map one-to-one onto it — know both:

| Lib                             | Directory group | `scope:*` tag    |
| ------------------------------- | --------------- | ---------------- |
| `feature/*`                     | `feature`       | `scope:frontend` |
| `shared/ui`                     | `shared`        | `scope:frontend` |
| `shared/mock`, `shared/utility` | `shared`        | `scope:shared`   |
| `core/*`                        | `core`          | `scope:shared`   |
| `prisma/client`                 | `prisma`        | `scope:prisma`   |
| `server/*`                      | `server`        | `scope:server`   |

`core/*` and `shared/{mock,utility}` are browser-safe (`scope:shared`);
`shared/ui` is `scope:frontend` because it imports Angular. A lib's tag is
what determines what it may depend on — set it to match this table when you
generate a new one (the generator does not infer it).

## Dependency Boundaries

The `@nx/enforce-module-boundaries` rule in `eslint.config.mjs` enforces these
constraints, keyed on the `scope:*` tag (quoted verbatim):

| `sourceTag`      | Constraint                                                 |
| ---------------- | ---------------------------------------------------------- |
| `scope:server`   | `notDependOnLibsWithTags: ['scope:frontend', 'scope:web']` |
| `scope:prisma`   | `notDependOnLibsWithTags: ['scope:frontend', 'scope:web']` |
| `scope:frontend` | `notDependOnLibsWithTags: ['scope:server']`                |
| `*` (fallback)   | `onlyDependOnLibsWithTags: ['*']` (permissive)             |

In plain terms:

- **Server and Prisma code must not reach into frontend or the web app** —
  this is what keeps `prisma/client`'s root barrel browser-safe and the
  server libs off the client bundle.
- **Frontend code must not import server-only libs** (`server/*`). The Prisma
  client instance is reached through `@kookio/prisma-client/server`, itself
  blocked from frontend globs by a separate `no-restricted-imports` rule (see
  `12_prisma-zod.md`).
- Everything else falls through the permissive `*` rule.

There is **no** lint rule forbidding `shared` → `feature`; the boundary is
expressed only through the four `scope` tags above, not the directory groups.
Keep `shared/*` free of feature dependencies by convention (it is stateless
and feature-agnostic), but that specific direction is not lint-enforced.

## Library Generation Templates

### JS/TS Library — `@nx/js:lib`

For non-Angular libs: `server/*`, `prisma/*`, `core/*`, `shared/{mock,utility}`.

```bash
npx nx g @nx/js:lib <name> \
  --directory=libs/<group>/<name> \
  --importPath=@kookio/<group>-<name> \
  --bundler=tsc \
  --unitTestRunner=vitest \
  --linter=eslint \
  --no-interactive
# e.g. --directory=libs/server/trpc    --importPath=@kookio/server-trpc
#      --directory=libs/shared/utility --importPath=@kookio/shared-utility
```

### Angular Library — `@nx/angular:library`

For libs that import Angular: `feature/*` and `shared/ui`.

```bash
npx nx g @nx/angular:library <name> \
  --directory=libs/<group>/<name> \
  --importPath=@kookio/<group>-<name> \
  --unitTestRunner=vitest \
  --linter=eslint \
  --style=scss \
  --standalone \
  --no-interactive
# e.g. --directory=libs/feature/pantry --importPath=@kookio/feature-pantry
```

After generating, set the `tags` array in the new `project.json` to the right
`scope:*` (+ a `type:*` label) per the scope-tag table above — the generator
defaults to none, and `@nx/enforce-module-boundaries` only constrains a lib
once it carries a `scope` tag.

## Bundler Strategy

| Generator             | Bundler        | Reason                                                                |
| --------------------- | -------------- | --------------------------------------------------------------------- |
| `@nx/js:lib`          | `tsc`          | Correct type declarations, zero overhead, ideal for internal monorepo |
| `@nx/js:lib`          | `esbuild`      | Only for publishable libs or where bundle size matters                |
| `@nx/angular:library` | Vite (default) | Only supported bundler — does not accept `--bundler=tsc`              |

- Do not use `--bundler=tsc` with `@nx/angular:library` — it is ignored or causes errors
- Do not use `--buildable` if the library is only consumed internally within the monorepo

## Auto-Generated Targets

### `@nx/js:lib` with `--bundler=tsc`

| Target  | Executor                 | Notes |
| ------- | ------------------------ | ----- |
| `build` | `@nx/js:tsc`             | ✅    |
| `test`  | `@nx/vite:test` (vitest) | ✅    |
| `lint`  | `@nx/eslint:lint`        | ✅    |

### `@nx/angular:library` (without `--buildable`)

| Target       | Executor                 | Notes                                                                        |
| ------------ | ------------------------ | ---------------------------------------------------------------------------- |
| `build-deps` | `nx:noop`                | ⚠️ non-buildable — consumed directly via TS paths                            |
| `typecheck`  | `tsc --noEmit`           | ✅ cacheable                                                                 |
| `test`       | `@nx/vite:test` (vitest) | ✅ cacheable — **must be added manually, not generated automatically by NX** |
| `lint`       | `@nx/eslint:lint`        | ✅ cacheable                                                                 |
| `watch-deps` | continuous               | ✅ useful in dev                                                             |

## Gotcha: `vite:test` vs `test`

`@nx/angular:library` generates the test target with the name `vite:test`, not `test`.

```bash
nx run ui:vite:test   # ✅ correct
nx run ui:test        # ❌ does not exist
```

When running tests with `nx run-many -t test`, Angular libraries **will be silently skipped**
(no errors). This behavior is acceptable for an internal monorepo.

For consistency, add an alias in `project.json`:

```json
"targets": {
  "test": {
    "executor": "@nx/vite:test"
  }
}
```

## Gotcha: lazy-loading is scoped to the **whole lib**, not a sub-path

`@nx/enforce-module-boundaries` decides a project is "lazy" the moment **any**
consumer imports it dynamically (`await import('@kookio/feature-pantry/...')`).
From that point on, **every static import of the same lib** — even from the
component that owns the page — is flagged with:

```text
Static imports of lazy-loaded libraries are forbidden.
```

The check is at project granularity. Sub-path exports do not partition the
rule: `@kookio/feature-pantry/dialog` and `@kookio/feature-pantry` resolve to
the same NX project, so a dynamic import of one taints static imports of the
other. There is no per-symbol or per-file escape; the only options are:

1. **Don't lazy-load at all.** For bundles that are merely large but not
   prohibitive, this is usually the right call. If the cold-start cost of
   eager-loading is what's hurting you, a Playwright `timeout` bump or a
   smarter `globalSetup` warm-up is far cheaper than a structural split.
2. **Extract the lazy surface into its own lib** with a `type:lazy` tag, and
   make every consumer go through `import()`. This is correct only when the
   chunk is genuinely huge (think a Markdown editor, a chart library, an
   embedded WASM module) or when several pages would benefit from sharing
   the lazy split.

Pattern decision: bundle-size pain alone is not enough to justify the split.
The split has its own ongoing cost — a third lib to keep lint/test/typecheck
clean, an extra path mapping, and an `import()` wrapper at every call site
that can no longer use the synchronous `MatDialog.open(Component, {...})`
shape. Reach for it only when the alternative — eager-loading — has a
**measured** runtime impact that no warm-up or timeout fix can erase.

Real instance: `feature-pantry` ships `MatDatepicker` and `MatAutocomplete`
through the dialog. We tried lazy-importing `pantry-dialog.component.ts` to
shrink `/pantry`'s initial bundle. NX rejected the static imports of
`PantryItemComponent` and `PantryStore` the page still needed, so we
reverted and took the 60s test timeout instead — the right trade-off
for a marginal save.

## Key Differences Between Generators

| Aspect                    | `@nx/js:lib`       | `@nx/angular:library` |
| ------------------------- | ------------------ | --------------------- |
| Angular components        | ❌                 | ✅                    |
| Recommended bundler       | `tsc` or `esbuild` | Vite (default)        |
| Test target name          | `test`             | `vite:test`           |
| `--bundler=tsc` supported | ✅                 | ❌                    |
| Standalone components     | N/A                | `--standalone`        |
| SCSS                      | N/A                | `--style=scss`        |

## When to Use Which Generator

| Library content                                                  | Generator                                    |
| ---------------------------------------------------------------- | -------------------------------------------- |
| Angular components, directives, pipes (`feature/*`, `shared/ui`) | `@nx/angular:library`                        |
| Server code, tRPC routers, Prisma (`server/*`, `prisma/*`)       | `@nx/js:lib`                                 |
| Pure functions, helpers, labelers (`shared/utility`, `core/*`)   | `@nx/js:lib`                                 |
| A domain's stores + services                                     | colocate in its `feature/*` lib (no new lib) |

## Major upgrades: `nx migrate` and hard dependency gates

Drive an Angular/NX stack upgrade with `nx migrate latest` (writes
`package.json` + `migrations.json`, no install), then `npm install`, then
`nx migrate --run-migrations`. Lessons from the Angular 20→21 / NX 21→22 jump:

- **`nx migrate` knows AnalogJS and ngrx** (it bumped `@analogjs/*`, `zone.js`,
  and Vitest) but resolves a **conservative** set — it left AnalogJS, Vite,
  and ESLint a major/minor behind their latest. Pushing to absolute latest is
  a separate, manual step (confirm each is peer-compatible first).
- It also leaves real gaps: it did **not** bump `@ngrx/signals` (which Angular
  21 requires at v21) or `@analogjs/trpc`. Close those by hand, and sync every
  lib `package.json` that pins them — the `@nx/dependency-checks` rule fails
  the lint otherwise.
- **NX 22 split Vitest support into `@nx/vitest`** — the migration renames the
  test executor from `@nx/vite:test` to `@nx/vitest:test` across every
  `project.json` and adds the package.

### Hard upgrade gates (verified against peer deps)

Some majors are blocked by the meta-framework and cannot be bumped until the
gating package moves — don't burn time trying:

- **tRPC stays v10** — `@analogjs/trpc` (latest) still peers `@trpc/* ^10`.
- **marked stays v15** — `@analogjs/platform` peers `marked ^15`.
- **TypeScript stays 5.9** — `@angular/build@21` peers `typescript >=5.9 <6.0`.

Couplings that move as a unit: Angular 21 ⇒ AnalogJS 2.x + ngrx 21 + Vitest 4
(`@angular/build@21` peers `vitest ^4`); `prisma-zod-generator@2` ⇒ Prisma 7.

## General Rules

- Always use `--no-interactive` for reproducibility in CI
- Import **other** libraries via `@kookio/<lib-name>` — never via deep
  relative paths.
- Import **inside the same lib** via relative paths
  (`../../models/nav-item`), **never** via a custom alias like `@models`.
  `tsconfig.base.json` has `baseUrl: "."` (the monorepo root), and
  `@nx/enforce-module-boundaries` rejects any alias that does not map to
  a known NX project — including a self-referential
  `@kookio/feature-shell` import from inside `feature-shell`. Confirmed
  by lint: the alias is treated as a cross-boundary import and blocked.
  The `@kookio/<lib-name>` alias is reserved for _external_ consumers.
- Enforce dependency boundaries defined in `nx.json` with `@nx/enforce-module-boundaries`
- Run `nx run-many -t lint typecheck` before any PR
