# E2E Testing Guidelines

> **Status: Active** — Playwright suite lives in `apps/web-e2e/`; `global-setup.ts` warm-up and the `waitUntil:'commit'` rule are both in use (see `feedback_playwright-chromium-ssr.md` in memory). Note that `apps/web-e2e/src/` flattens specs into folders (`auth/`, `metrics/`, `helpers/`, `fixtures/`) rather than the `pages/` POM split described below — Page Objects are not formally used yet.

## Framework & Tools

- Playwright for all E2E tests
- Page Object Model (POM) for test organization
- Runs in CI/CD pipeline on every PR

## Philosophy

- E2E tests cover critical user journeys — not every UI interaction
- Test what unit/integration tests cannot: full flows, navigation, real API responses
- Keep E2E tests stable and deterministic — flaky tests must be fixed or removed immediately
- E2E tests are slow by nature — be selective about what gets tested at this level

## Page Object Model

### Base Page

- Define a `BasePage` with shared utilities:

```typescript
import { Page, Locator } from '@playwright/test';

export abstract class BasePage {
  constructor(protected readonly page: Page) {}

  async navigateTo(path: string): Promise<void> {
    await this.page.goto(path);
  }

  async waitForNetworkIdle(): Promise<void> {
    await this.page.waitForLoadState('networkidle');
  }
}
```

### Page Objects

- One class per page or major feature area:

```typescript
import { Page, Locator, expect } from '@playwright/test';
import { BasePage } from './base.page';

export class UsersPage extends BasePage {
  readonly usersList: Locator;
  readonly addUserButton: Locator;
  readonly searchInput: Locator;

  constructor(page: Page) {
    super(page);
    this.usersList = page.getByRole('list', { name: 'Users' });
    this.addUserButton = page.getByRole('button', { name: 'Add User' });
    this.searchInput = page.getByRole('searchbox', { name: 'Search users' });
  }

  async searchFor(term: string): Promise<void> {
    await this.searchInput.fill(term);
    await this.searchInput.press('Enter');
  }

  async expectUserVisible(name: string): Promise<void> {
    await expect(this.usersList.getByText(name)).toBeVisible();
  }

  async expectUserCount(count: number): Promise<void> {
    await expect(this.usersList.getByRole('listitem')).toHaveCount(count);
  }
}
```

- Define locators as class properties — not inline in test methods
- Expose semantic methods that describe user intent — not low-level interactions
- Keep assertions inside Page Object methods where they belong to the page contract
- Do NOT leak Playwright internals into tests — tests should read like user stories

### Fixtures

- Use Playwright fixtures for authenticated sessions and shared setup:

```typescript
import { test as base } from '@playwright/test';
import { UsersPage } from '../pages/users.page';

type Fixtures = {
  usersPage: UsersPage;
};

export const test = base.extend<Fixtures>({
  usersPage: async ({ page }, use) => {
    // Perform login via API to avoid UI login on every test
    await page.request.post('/api/auth/login', {
      data: { email: process.env.TEST_USER, password: process.env.TEST_PASSWORD },
    });
    const usersPage = new UsersPage(page);
    await usersPage.navigateTo('/users');
    await use(usersPage);
  },
});

export { expect } from '@playwright/test';
```

- Authenticate via API request in fixtures — never via UI login for every test
- Store auth state with `storageState` for session reuse across tests

## Writing Tests

- Use the custom fixture in tests — not raw `test` from Playwright:

```typescript
import { test, expect } from '../fixtures';

test.describe('Users page', () => {
  test('should display users list', async ({ usersPage }) => {
    await usersPage.expectUserCount(10);
  });

  test('should filter users by search term', async ({ usersPage }) => {
    await usersPage.searchFor('John');
    await usersPage.expectUserVisible('John Doe');
  });
});
```

- One user journey per test — avoid long multi-step tests that test many things at once
- Use `test.describe()` to group related scenarios
- Use `test.beforeEach()` for navigation setup — not for data setup (use fixtures)

## Locators

- Always prefer semantic locators in order of priority:
  1. `getByRole()` — most resilient, reflects accessibility tree
  2. `getByLabel()` — for form fields
  3. `getByText()` — for static content
  4. `getByPlaceholder()` — for inputs without labels
  5. `getByTestId()` — last resort, only when semantic locators are impossible
- Never use CSS selectors or XPath — they are brittle and couple tests to implementation
- Never locate by Angular component class names or internal DOM structure

## Assertions

- Always use Playwright's `expect()` with auto-retry assertions:

```typescript
// ✅ auto-retries until condition is met or timeout
await expect(locator).toBeVisible();
await expect(locator).toHaveText('John Doe');
await expect(locator).toHaveCount(5);

// ❌ no auto-retry, causes flakiness
expect(await locator.isVisible()).toBe(true);
```

- Never use `page.waitForTimeout()` — use explicit assertions or `waitForLoadState()`

## CI/CD

- Run E2E tests in headless mode in CI
- Use `--shard` flag to parallelize across CI workers:

```yaml
npx playwright test --shard=1/4
```

- Store test artifacts (screenshots, videos, traces) on failure:

```typescript
  // playwright.config.ts
  use: {
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
    trace: 'retain-on-failure',
  }
```

- Never commit `test-results/` or `playwright-report/` — add to `.gitignore`
- Use environment variables for all credentials — never hardcode in test files
- E2E tests run against a dedicated test environment — never against production

## Angular SSR + Playwright Chromium — Known Failure Patterns

Chromium aborts navigations more aggressively than Firefox/WebKit. Two distinct failure modes exist when testing AnalogJS SSR apps:

### 1. Angular router redirect during hydration → `ERR_ABORTED`

Routes with guards (`authGuard`, `guestGuard`) fire a programmatic router redirect during SSR hydration. Chromium aborts the original `page.goto()` navigation; Firefox/WebKit wait for the chain to complete.

Fix: add `{ waitUntil: 'commit' }` to every `page.goto()` that navigates to a guarded route or any route that may trigger a client-side redirect:

```typescript
// ✅ correct — resolves as soon as HTTP headers are received, before Angular hydrates
await page.goto('/pantry', { waitUntil: 'commit' });
await page.waitForURL((url) => url.pathname === '/login');

// ❌ default 'load' — Chromium aborts when Angular router fires redirect mid-navigation
await page.goto('/pantry');
```

### 2. Vite SSR cold-start compilation → timeout on first parallel batch

In dev mode, Vite compiles SSR modules on demand. When the first batch of parallel tests all navigate immediately (no async fixture setup), the compilation of multiple routes can take longer than the test timeout.

Fix: add a `globalSetup` that pre-warms all routes before any worker starts:

```typescript
// apps/web-e2e/global-setup.ts
const BASE_URL = process.env['BASE_URL'] ?? 'http://localhost:4200';
const ROUTES = ['/', '/about', '/login', '/register', '/pantry', '/account', '/admin'];

const warmRoute = async (path: string): Promise<void> => {
  try {
    await fetch(`${BASE_URL}${path}`, { signal: AbortSignal.timeout(120_000) });
  } catch {
    // warm-up is best-effort
  }
};

export default async (): Promise<void> => {
  await Promise.all(ROUTES.map(warmRoute));
};
```

Register it in `playwright.config.ts`:

```typescript
export default defineConfig({
  globalSetup: require.resolve('./global-setup'),
  globalTeardown: require.resolve('./global-teardown'),
  // ...
});
```

Playwright guarantees the `webServer` is running before `globalSetup` executes. When new routes are added to the app, add them to `ROUTES` in `global-setup.ts`.

### 3. `app.config.ts` barrel imports amplify cold-start cost across every route

`app.config.ts` is on the SSR critical path of **every** route — every
import there gets evaluated for every page Vite compiles. Combine that
with two Vite dev-mode realities and you get a non-obvious cold-start
amplifier:

- `export *` barrels are not tree-shaken in Vite dev. Each re-export
  evaluates eagerly when anything in the barrel is imported, so a single
  `import { TOKEN } from '@kookio/feature-x'` drags every component the
  barrel re-exports.
- Material modules (`MatDatepicker`, `MatDialog`, `MatAutocomplete`, …)
  cascade into substantial sub-graphs. A page that doesn't render them
  still pays for compiling them.

The trap: an `InjectionToken` import in `app.config.ts` looks free (it's
a static value, no logic). But if it lives next to a heavy component in
the same barrel, the cost lands on every route's first SSR hit. **The
unit-test and typecheck suite cannot detect this** — both run in
isolation. It surfaces only at cold-start in dev or E2E, exactly where
Playwright's 30s timeout punishes you.

Practical rules:

1. **Audit `app.config.ts` periodically.** Every import there multiplies
   by the number of routes. Ask "what does this drag transitively?"
   before adding a new line.
2. **Segment feature-lib barrels** that mix a "light" surface (token,
   types) with a "heavy" surface (components pulling Material). Tokens
   and DTOs go behind a sub-path (e.g. `@kookio/feature-pantry/trpc`);
   components stay on the main barrel and load only when the page that
   uses them does.
3. **Scope `provide*` calls to the deepest functional level.** App-level
   providers carry the same per-route tax. `provideNativeDateAdapter()`
   belongs on the form component that owns the datepicker, not on the
   root config.
4. **Treat SSR cold-start as a first-class test.** Green typecheck + green
   vitest do not imply green E2E. When a feature lands with a wave of new
   Material imports, measure cold `curl /login` against a freshly purged
   Vite cache before assuming it's fine:

   ```bash
   rm -rf node_modules/.vite
   npx nx serve web > /tmp/dev.log 2>&1 &
   until grep -qE "Local:" /tmp/dev.log; do sleep 1; done
   curl -sf -o /dev/null -w "/login cold: %{time_total}s\n" \
     http://localhost:4200/login --max-time 90
   ```

   A login page that takes >15s warm is already on the wrong side of the
   cold-start budget once parallel workers pile on.

Generalised principle: **the cost of an import is not local — it scales
with how often the module that contains it is evaluated**. App-level
providers and barrel re-exports amplify the cost; component-level
providers and sub-path imports isolate it. Reach for the latter the
moment the former crosses 10s of compile time on any route.

## General Rules

- Tests must be independent — no shared mutable state between tests
- Tests must be deterministic — same result every run
- Flaky tests are bugs — treat them as such
- Do not duplicate unit test coverage in E2E tests
- Keep Page Objects focused — one page, one class
- Review E2E coverage as part of PR review
